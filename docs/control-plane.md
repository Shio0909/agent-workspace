# 控制面机制

本文说明控制面新增的四组机制（幂等操作记录、审计日志、分阶段回收、后台调度）和四项工程能力（指标、优雅停机、健康与就绪分离、启动配置校验）的设计取舍、不变量，以及**在什么故障下能保证什么、不能保证什么**。

约定：本文只描述当前实现。没有实现的能力不会被写成"保证"。

---

## 1. 幂等操作记录

### 目的

`SetDesired` 本来就对"重复设置同一个目标状态"幂等，但那依赖状态本身可比较。调用方在网络超时后重试时，需要的是"这次请求是否已经执行过"这个**跨请求**的答案，而不是让控制面去猜。幂等键把这个判断交给调用方。

### 数据结构与键的选择

```
Operation{BizID, Workspace, Type, Status, Generation, Error, StartedAt, FinishedAt}
Status: processing -> success | failed   （两个终态都不可逆）
```

- **BizID 是唯一的幂等键**，`Type` 只是记录的一部分。这样一个 biz_id 对应一次调用方请求；`FinishOperation(op, err)` 收尾的是 `BeginOperation` 返回的那条记录（见下文 `Generation`）。
- 同一个 biz_id 换了 `Type` 或换了工作区 → `ErrConflict`。控制面不猜调用方想要什么，直接拒绝，避免"用旧的键执行新的动作"这种最危险的组合。

### 状态机

| 已有记录 | `BeginOperation` 的返回 | HTTP |
| --- | --- | --- |
| 不存在 | `err == nil`，调用方必须执行动作 | 202 + 工作区 |
| `processing` 且未超存活上限 | `ErrOperationInProgress` | 202 + 幂等记录 |
| `success` | `ErrOperationSucceeded` | 200 + 幂等记录 |
| `failed` | `ErrOperationFailed` + 原始错误文本 | 409 + 原始错误文本 |

- **调用方只有在 `err == nil` 时才允许执行动作**，执行完必须用 `BeginOperation` 返回的记录调用 `FinishOperation`。收尾是"先到先得"：重复收尾不会把 `success` 翻成 `failed`。
- **failed 是终态**。同一个 biz_id 重放失败请求会拿到第一次的错误，不会重试。要重试就换一个新的 biz_id。这是刻意的：如果 failed 可以复用，那么"客户端在超时后重试"和"服务端已经执行了一半"就无法区分。
- **processing 记录有存活上限**（`OperationLease`，默认 10 分钟）。控制器在执行动作中途崩溃会留下一条永远不会自己结束的记录，不接管就等于永久锁死这个 biz_id。超过上限后，后来的请求会接管它。
- **状态转换在存储锁内按最新记录判定**。收尾要求记录此刻仍是 `processing` 且仍是自己那一代；接管要求记录仍是 `processing`、仍是读到的那一代、租约确实已过。调用方更早读到的快照只用来提出请求，不作为写入依据，所以交错执行不会把终态记录改回去。
- **`Generation` 标识当前持有记录的那一次执行**：首次占用为 1，每次接管加 1。被接管的旧持有者迟到的收尾得到 `ErrOperationSuperseded`，结果不会写入，也就不会给新持有者仍在执行的操作定性。记录已进入终态时，旧持有者的收尾和其他重复收尾一样是无操作。升级前落盘的记录没有该字段（按 0 处理），仍可被接管。

### 存储与保留

- 工作区与幂等记录落在数据目录的 `state.db`：bbolt 的 `workspaces` 和 `operations` bucket，每次只写发生变化的记录；并发的不同记录共享一个事务和一次 fsync。
- 检查与插入由 `Store` 在同一事务边界内完成；单进程由数据目录上的建议锁保证（第二个控制器进程会被直接拒绝）。旧版 JSON 快照首次打开时导入，并保留为 `*.migrated`。
- 记录数量上限 `MaxOperations`（默认 10000），超出后按完成时间淘汰最旧的**终态**记录。`processing` 记录永不淘汰：淘汰一条正在执行的记录等于允许它被再执行一次；如果所有记录都在执行中，宁可超限也不误伤。

### 保证与不保证

保证：

- 同一个 biz_id 在记录被淘汰之前，最多只产生一次副作用（前提是副作用通过控制面的状态写入表达）。
- 并发提交同一个 biz_id 时，只有一个调用方会拿到 `err == nil`。这是锁内的检查并插入，不依赖调用方的重试间隔。

不保证：

- **不保证跨 biz_id 的去重**。调用方用两个不同的 biz_id 提交同一件事，控制面会执行两次。
- **不保证永久幂等**。记录被淘汰（超过上限）之后，同一个 biz_id 会被当成新请求。
- **接管意味着可能重复执行**。崩溃超过 `OperationLease` 后，原请求可能仍在别处运行；控制面假设动作本身幂等（写入目标状态），而不是"只扣一次钱"。
- **不保证重放的 HTTP 状态码与第一次一致**。记录里只保存错误文本，重启后无法还原错误类型，所以重放失败统一返回 409 并带上原始消息。

## 2. 审计日志

### 格式与写入

- `AuditEvent{At, Actor, Action, Workspace, Detail, Result}`，一行一条 JSON（JSONL），落在数据目录的 `audit.jsonl`。
- 每个文件只追加，不重写已有记录。当前文件达到 8 MiB 前轮转，保留当前文件与最近 4 个归档；超过保留窗口的历史会删除，长期审计需另行归集。既有超大文件不会被截断，而是整份归档。归档使用递增序号，不依赖事件时间或系统时钟排序。
- 单条编码后记录最多 1 MiB，超限拒绝并走既有审计失败计数，避免写入后无法查询。
- 每次追加都 `fsync`。审计是同步写：调用方宁可多等一次磁盘，也不希望崩溃后查不到刚刚发生的状态变更。
- 打开文件时检查最后一个字节：如果不是换行（上次崩溃留下半行），先补一个换行。**补这一行的意义是把损坏限制在"丢半行"**，否则下一次追加会直接接在半行后面，把新记录也一起写坏。

### 覆盖的动作

`create`、`start`、`stop`、`restart`、`delete`、`lease-acquire`、`lease-release`、`idle-stop`、`expire`、`suspend`、`hard-delete`，另有 `resume`（挂起后人工续期恢复）和 `expiry-set`（只改租期不改状态）。

几个动作的边界是刻意区分的：

- `delete` 记录**用户显式删除请求被接受**（意图落盘）；`hard-delete` 记录**运行时资源真的被删除**（含 PVC），Detail 里带上触发者（`user-requested` / `grace period elapsed`）。所以一次用户删除会有两条记录：意图和完成。
- `expire` 记录**判定过期并转入挂起意图**；`suspend` 记录**工作负载已缩容到 0、存储保留**。
- 失败的回收（例如缩容失败）用 `Result=error` 记录一次，**同一个故障持续期间不会每轮重复记录**，否则后端挂掉会把审计日志刷爆。

### 查询

`GET /v1/audit?workspace=&action=&since=&until=&limit=`（`since` 是闭区间、`until` 是开区间，都是 RFC3339；`limit` 上限 1000）。查询在短暂持锁期间打开保留文件并记录各文件长度，随后释放锁扫描。轮转或删除归档不影响已经打开的查询快照，查询开始后的追加也不混入本次结果。按追加顺序返回，不按事件时间重排；`limit` 仍取前 N 条。写坏的行会被跳过。查询存活期间可能暂时保留已删除文件的磁盘空间，直到查询关闭文件。

轮转在“旧文件已重命名、新文件未创建”时发生进程退出，可以在重启时创建当前文件并继续读取归档。这是进程中断恢复测试，不代表已经验证断电或文件系统损坏恢复。

### 保证与不保证

保证：

- 已经返回成功的追加，在进程重启后仍可查询。
- 追加不会破坏已有内容。

不保证：

- **审计与状态变更不是事务**。实现是"先改状态、再写审计"，两步之间崩溃会丢掉那条记录。写审计失败既不回滚动作，也不静默：错误会进日志，并计入 `nc_audit_failures_total`。
- **崩溃最多丢失一条记录**（写了一半的那条）。补换行可以避免它连带写坏下一条，但不等于不丢。
- **共享令牌的 Actor 不是身份认证**。持共享令牌的调用方可以通过 `X-Actor` 声称任意身份，它只用于归属和排查。持作用域令牌的调用方不能自报：审计里记录的是 `token:<令牌名>`，见第 11 节。
- 查询是 O(文件大小) 的全量扫描，没有索引，也没有分页游标（只有 `limit`）。

## 3. 分阶段回收

### 生命周期

```
running --空闲超时--> stopped          （保留 PVC）
running/stopped --租期到期--> suspended（保留 PVC，标记过期，人工可恢复）
suspended --宽限期满--> deleted        （硬删 Deployment/Service/PVC）
```

| 字段 | 含义 |
| --- | --- |
| `ExpiresAt` | 租期截止时间；零值表示永不过期。 |
| `SuspendedAt` | 进入挂起态的时刻，宽限期从这里计时。必须持久化，否则重启会把宽限期重新计时。 |
| `Desired=deleted` + `Phase=deleted` | 墓碑：资源已删除，记录保留。 |

### 谁可以推进状态

- `SetDesired` 只接受 `running` / `stopped` / `deleted`。`suspended` **不是外部可以指定的意图**，它是控制面的回收决策。
- `running/stopped -> suspended` 与 `suspended -> deleted` 只发生在 `Reconcile` 里，也就是只由调度循环或代理路径的唤醒触发。
- 人工恢复的唯一入口是 `POST /v1/workspaces/{id}/expiry`：给一个未来的截止时间（或清除截止时间）会把挂起态改回 `stopped`。恢复不重建存储——挂起阶段从未删除它。

### 不变量

1. **suspended 阶段必须保留 PVC**。这一跳调用的是 `Runtime.Stop`（接口约定：Stop 必须保留存储），`Runtime.Delete` 在这条路径上完全不可达。
2. **只有 `Desired=deleted` 才会调用 `Runtime.Delete`**。触发者只有两个：用户显式删除，或宽限期满。
3. **回收只在工作区空闲时推进**（无在途请求、无有效租约）。租期到期不足以掐断一个正在运行的任务；推迟不会丢状态，因为截止时间仍然在过去。
4. **先落盘意图，再做运行时动作**。回收决策写入持久化 Store 之后才会调用运行时，所以在这里崩溃不会留下"看起来还在运行、实际资源已删"的状态。
5. **墓碑不会被再次回收**：`Phase=deleted` 的工作区直接跳过。

### 保证与不保证

保证：

- 挂起态不会删除存储；只有删除态会。
- 控制器重启不会重置宽限期计时（`SuspendedAt` 持久化），也不会因为重启就立刻删除挂起的工作区（启动静默期）。
- 过期的工作区不会被 `start` / `restart` / 代理请求唤醒：它们返回 410 并要求先续期。拒绝发生在修改状态之前，所以过期的服务不会靠一次请求复活。

不保证：

- **不保证存储一定存在**。控制面只保证"不主动删除"；集群外部的删除、PV 回收策略、节点故障都不在控制面范围内。
- **不保证回收准时**。实际时刻 = 轮询周期 + 单轮上限 + 排队，见下一节。
- **不保证删除一定成功**。删除失败会保留 `Desired=deleted` 并重试，工作区停留在 `Phase=error`，审计里有一条 `Result=error` 的 `hard-delete`。

## 4. 后台调度

`Scheduler` 是控制面唯一的周期性驱动。一轮扫描经由 `Reconcile` 同时完成四件事：对账运行时、空闲缩容、过期挂起、宽限期满硬删。

周期扫描是兜底。`runtime` 提供事件源时，Deployment/Pod watch 事件会进入去重、指数退避的 event queue；`start`/`stop`/`restart`/`delete` 写入 intent 后也会立即入队。事件路径不承担时间驱动语义，事件丢失时仍由 scheduler 收敛。

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `-reconcile` | 5s | 轮询周期。 |
| `-round-timeout` | 1m | 单轮执行上限：到点后不再派发新的工作区，等在途对账收尾。 |
| `-batch` | 64 | 每批从内存状态索引里取多少条工作区。 |
| `-sweep-concurrency` | 4 | 同时执行多少条对账（与旧版固定 4 路并发一致）。 |
| `-startup-grace` | 1m | 进程启动后的回收静默期。 |
| `-grace` | 24h | 挂起后的宽限期。 |

- **批量扫描**：`Store.Scan(after, limit)` 用 ID 作为游标分页推进，一轮里同时展开的工作区数量由页大小决定，而不是由工作区总量决定。（注意：`Store` 启动时加载一份内存索引，分页限制的是工作集与并发，不是磁盘 IO。有序索引只在 ID 集合变化时重建，否则频繁对账会让每页都重排一次全量。）
- **失败不中断整轮**：单条失败只计数、记日志、继续处理其余工作区。
- **启动静默期**：`StartupGrace` 内不做挂起与硬删。重启时工作区可能正在恢复，或者调用方正准备续期，第一轮扫描不应该把它们当垃圾。空闲缩容另有一个基于 `-idle` 的重启宽限期，两者独立。
- 一轮结束后按统计打日志：正常走 Debug，有失败或超时走 Warn。

不保证：

- **不保证"到点就执行"**。回收的延迟上限是"周期 + 单轮上限 + 该条工作区在轮次里的排队时间"。
- **不保证一轮覆盖所有工作区**。单轮超时后剩下的工作区留到下一轮。
- 指标与审计只反映"这一轮做了什么"，不做跨实例聚合。

## 5. 可观测性

`GET /metrics` 输出 Prometheus 文本格式，**需要控制令牌**（它会暴露工作区数量）。手写而不是引入客户端库：当前只需要 counter、gauge 和固定桶 histogram，标准库足够。

| 指标 | 类型 | 含义 |
| --- | --- | --- |
| `nc_workspaces{phase}` | gauge | 按 phase 计数（抓取时从快照算）。 |
| `nc_operations{status}` | gauge | 幂等记录按状态计数。 |
| `nc_leases` | gauge | 未过期的租约数量。 |
| `nc_reconcile_total` / `nc_reconcile_failures_total` | counter | 对账次数与失败次数（含命中就绪端点缓存的那些）。 |
| `nc_idle_stops_total` | counter | 空闲缩容次数。 |
| `nc_expirations_total` | counter | 判定过期并转入挂起的次数。 |
| `nc_suspensions_total` | counter | 工作负载缩容到 0、存储保留的次数。 |
| `nc_hard_deletes_total` | counter | Deployment/Service/PVC 被删除的次数。 |
| `nc_operations_started_total` / `nc_operation_replays_total` / `nc_operation_takeovers_total` | counter | 首次提交 / 重放 / 接管陈旧记录。 |
| `nc_audit_failures_total` | counter | 写审计失败的次数。 |
| `nc_tokens_total{profile,kind}` | counter | 心跳上报的 token 增量，`kind` 为 `prompt` 或 `completion`。没有工作区标签（基数）；上报回退的那段不计入。 |
| `nc_budget_suspensions_total{profile}` | counter | 因 token 预算用尽被挂起的次数。 |
| `nc_event_reconciles_total` / `nc_event_reconcile_failures_total` | counter | 事件驱动对账次数，以及失败并重新入队的次数。 |
| `nc_workspace_acquire_seconds` | histogram | 请求等待可用 endpoint 的耗时。 |
| `nc_workspace_start_seconds{phase}` | histogram | 冷启动的 schedule、pull、ready、total 分阶段耗时。 |
| `nc_kube_api_requests_total{verb,resource}` | counter | 控制器发送到 Kubernetes API 的请求，用来验证 informer cache 的效果。 |

计数器是进程内的，**重启归零**；gauge 每次抓取从快照重算，所以不会漂移。标签按值排序输出，两次抓取可以直接比对。

## 6. 健康与就绪

| 端点 | 鉴权 | 含义 |
| --- | --- | --- |
| `GET /health` | 无 | 进程存活。只要进程还在就返回 200。 |
| `GET /ready` | 无 | 依赖可用：`client-go` Discovery 能连上 API Server。不可达返回 503。 |

两者分开的意义：进程活着但 API 不可达时，应该把实例摘出流量，而不是让编排系统重启一个其实健康的进程。探针请求来自编排系统，拿不到业务凭据，所以这两个端点不校验控制令牌。

- 单次探测上限 `ProbeTimeout`（默认 3s），结果缓存 `ReadyTTL`（默认 2s），避免频繁探针变成对 API 的压测。
- 就绪**不**由"最近一次对账是否失败"推导：连不上集群和某个工作区对账失败是两件事。

## 7. 优雅停机

收到 SIGINT/SIGTERM 后依次：

1. 取消根 context：调度循环不再开始新一轮，HTTP 服务不再接受新请求。
2. `server.Shutdown`，上限 10s；超时则强制关闭（在途的长连接 SSE 会被截断）。
3. 等在途对账收尾（`Scheduler.Run` 返回），上限 10s。

等待有上限是刻意的：对账是幂等的，没跑完的部分下次启动会重做，所以"超时放弃"不会丢状态，只会延后。停机超时会打一条 Warn。

## 8. 启动配置校验

非法配置在启动阶段直接失败退出，而不是带着坏参数跑到几小时后才暴露：

- 共享令牌长度、监听地址、数据目录、profile 路径非空，命名空间是合法 DNS 标签。
- 给了 `-tokens` 时，令牌文件必须能解析、不含未知字段、每个条目都有作用域，且不能和共享令牌相同（见第 11 节）。
- `-idle`、`-grace`、`-reconcile`、`-round-timeout` 必须为正，`-startup-grace` 不得为负。
- `-batch` 在 [1, 10000]、`-sweep-concurrency` 在 [1, 64]。
- 每个 profile 必须通过 `Profile.Validate()`，且**拒绝未知字段**——profile 决定镜像、挂载和资源，一个拼错的键静默生效比启动失败危险得多。

## 9. 测试覆盖与已知盲区

覆盖（`go test -race ./...`）：

- 幂等：并发提交同一 biz_id 只执行一次；重放成功/失败/进行中的记录；同一 biz_id 换类型或换工作区被拒；陈旧 processing 记录被接管（并发接管只有一个赢家，用过期快照接管不能让终态记录复活）；收尾先到先得（含并发交错）；被接管的旧持有者不能收尾新一代；保留上限只淘汰终态记录；快照跨重启保留。
- 审计：全生命周期动作、跨重启可见、按工作区/动作/时间/条数过滤、半行容错、只追加、写失败只计数不回滚、同一故障不重复记录。
- 回收：挂起保留存储（`Runtime.Delete` 调用次数为 0）、宽限期满才硬删、宽限期跨重启延续、启动静默期阻止回收、租约阻止到期挂起、显式删除跳过宽限期、过期工作区拒绝唤醒与续期恢复。
- 调度：分页不重不漏、批大小与并发上限（含并发确实发生）、单轮超时、单条失败不中断、跳过墓碑、`Run` 能被取消。
- 工程项：指标文本格式与取值、就绪与存活分离、`/metrics` 鉴权、审计与续期端点、启动配置校验。
- 事件与缓存：event queue 去重、退避、shutdown 唤醒、intent/runtime event 触发、Acquire 事件唤醒；informer cache 的 sync、cache-only read、cache miss、fallback 和冷启动时间戳。
- 故障注入：随机 crash/restart、运行时故障、丢失响应，以及 6 个故意植入的 mutant。

盲区（没有测到，也不假装测到）：

- **kube 层使用 `client-go/fake` 做 typed object 单元测试，并提供 kind e2e smoke test**；生产集群的长期稳定性仍不在单元测试范围内。
- **时间相关行为使用注入的假时钟**。真实时钟下的长周期（24h 宽限期）没有端到端验证，也没有跨越真实时间的时钟漂移测试。
- **chaos test 是进程内关闭并重开 Controller/Store，不是真正 kill 进程**；它覆盖状态恢复，但不覆盖 OS 进程退出、文件系统断电或 kubelet 行为。
- **fsync 只验证了被调用**，没有断电级别的持久化验证（单元测试无法模拟掉电）。
- **没有多进程并发测试**。数据目录的 flock 只验证了"第二个进程被拒绝"，没有验证两个进程同时写会怎样（设计上不允许）。
- **Prometheus 文本没有用 promtool 校验**，只做了自解析与格式断言。
- **HTTP 层的并发幂等测试依赖调度**，是概率性的，不是形式化验证。
- 指标重启归零、没有跨实例聚合；审计查询是线性扫描，没有分页游标。

## 10. 故障下的行为速查

| 故障 | 保证 | 不保证 |
| --- | --- | --- |
| 控制器在动作中途崩溃 | 意图已落盘的动作会在下次启动被重做；幂等记录超过存活上限后可被接管 | 不会重复执行；放弃中的动作可能已经产生副作用 |
| 后端 API 不可达 | 对账失败被计数并保留错误，下一轮重试；`/ready` 返回 503 | 回收会按时发生（重试期间会推迟） |
| 写审计失败 | 动作照常完成，失败被计数并记录日志 | 审计完整（会丢这条记录） |
| 状态数据库损坏 | 启动直接失败，不会静默重置数据 | 自动恢复 |
| 审计文件末尾有半行 | 打开时补换行，损坏被限制在一条记录内；坏行被查询跳过 | 半行那条记录可读 |
| 删除存储前进程被杀 | 意图（`Desired=deleted`）仍在，重启后重删 | 删除已完成 |
| 停机超时 | 未完成的对账在下次启动重做 | 在途请求一定完成 |
| 预算越线后控制器立刻崩溃 | 挂起先落盘再停工作负载；重启后不重复审计、不重复计数，下一轮对账停掉负载 | 越线前最近一个刷新间隔内的用量（崩溃会丢，但不会丢挂起） |
| 工作负载丢卷后从 0 重新计数 | 控制器保留已记录的较大值，写一条 `usage-regressed` 审计 | 补上回退之前的用量（无法区分重置与错误数字） |

## 11. 控制令牌与作用域

默认只有一个共享令牌（环境变量 `AGENT_WORKSPACE_TOKEN`），持有者可以对任何工作区做任何事。多个调用方（例如不同团队的 CI）共用它时，一方泄露等于全部泄露，审计里也分不清是谁做的。

可选的 `-tokens` 文件加入**作用域令牌**。共享令牌保持原样，作为管理员令牌留给运维；不给 `-tokens` 时行为与之前完全一致。

### 配置

```json
[
  {"name": "team-a-ci", "sha256": "<64 位十六进制>", "workspaces": ["team-a-*"], "profiles": ["agent"]},
  {"name": "agents",    "sha256": "<64 位十六进制>", "profiles": ["agent"]}
]
```

```bash
TOKEN=$(openssl rand -hex 32)                       # 交给调用方
printf %s "$TOKEN" | shasum -a 256 | cut -d' ' -f1  # 写进文件（Linux 用 sha256sum）
```

- 文件里只有 SHA-256 摘要，没有令牌本身。文件泄露不会泄露可用的令牌；摘要无法反推，所以令牌必须是高熵随机串（服务端拿不到明文，无法检查长度）。
- `workspaces` 是精确的工作区 ID，或 `前缀*`。单独的 `*` 被拒绝，因为它等于没有限制。
- `profiles` 必须是 `profiles.json` 里存在的名字，拼错会在启动时报错。
- 两者都给时取**交集**。两者都不给的条目被拒绝：那是第二个管理员令牌，而管理员令牌只有一个。
- 拒绝未知字段（拼错的 `workspace` 若被忽略，令牌会比本意宽得多）、重名、重复摘要，以及和共享令牌相同的条目（共享令牌先匹配，那条限制永远不会生效）。
- 文件在启动时读取。增删或吊销令牌要改文件并重启控制器。Kubernetes 里把文件放进 ConfigMap 或 Secret，挂载后加 `-tokens` 参数即可。

### 规则

| 路由 | 作用域令牌 |
| --- | --- |
| `/v1/workspaces/{id}/*`、`/w/{id}/*` | 工作区在作用域内才放行，否则 404 |
| `GET /v1/workspaces` | 只列出作用域内的工作区 |
| `POST /v1/workspaces` | `id` 和 `profile` 都在作用域内才能创建，否则 403 |
| `GET /v1/audit` | 必须带 `workspace` 且在作用域内：不带返回 403，不在作用域返回 404 |
| `GET /metrics` | 403，只有管理员能读 |
| `/health`、`/ready` | 不需要令牌，和之前一样 |
| 以后新增的、不带 `{id}` 的路由 | 默认只给管理员；要对作用域令牌开放，必须显式用 `open` 注册并自己做作用域判断 |

- **越权的 404 与不存在的工作区逐字节相同**（测试断言）。作用域令牌无法借响应差异探测别的租户有哪些工作区。创建和审计的 403 不涉及现有工作区，所以不需要伪装。
- **审计归属由令牌决定**：作用域令牌的 actor 是 `token:<令牌名>`，忽略 `X-Actor`。共享令牌自报的 `X-Actor` 如果带 `token:` 前缀会被忽略，所以审计里带这个前缀的记录确实来自对应的令牌。
- 比较方式：先比共享令牌，再把请求里的令牌哈希后与每个摘要做常量时间比较，命中后不提前退出。日志只记录令牌名，不记录令牌或摘要。

### 保证与不保证

保证：

- 作用域令牌不能读、写、停止、删除、升级、轮换凭据或转发流量到作用域外的工作区，也看不到它们。
- 作用域令牌不能创建作用域外的工作区。创建被拒绝时不会留下任何东西。
- 忘记给新路由加限制时，结果是拒绝作用域令牌，而不是放行。

不保证：

- **这是授权，不是租户隔离**。作用域内的令牌仍可通过 `/w/{id}/` 访问该工作区里的 agent；工作区之间的网络隔离由 `deploy/controller.yaml` 里的 NetworkPolicy 提供（只放行控制器访问工作区 Pod，需要 CNI 真正执行；`scripts/kind-isolation.sh` 验证），控制面本身不做网络隔离，见 SECURITY.md。
- **令牌没有过期时间**。吊销靠改文件并重启。
- **幂等键 `biz_id` 是全局的**，不按令牌隔离。两个令牌对不同工作区用了同一个 `biz_id`，后到的会得到 409。调用方应使用带自己前缀的 `biz_id`。
- **共享令牌仍然无所不能**。它应当只留给运维，不要发给调用方。
- 没有速率限制，一个作用域令牌仍可以占满控制面。

## 12. 用量计量与 token 预算

工作负载在心跳回复里可选地带上累计用量 `usage:{prompt_tokens,completion_tokens,total_tokens}`；控制器只读这三个数，不关心它来自哪个模型。完整契约、校验规则和端点见 [upgrade-and-heartbeat.md](upgrade-and-heartbeat.md)。这里只记录取舍和不变量。

- **累计且单调**：计数器由工作负载持有，控制器取逐字段最大值，从不把心跳相加。丢失、重复、乱序的心跳不会改变总数。
- **低于已记录值的上报被忽略**：审计一条 `usage-regressed`（每次回退只记一次），回退期间的 token 不进 `nc_tokens_total`。
- **预算越线立即落盘**：`total_tokens >= token_budget` 时，工作区先被持久化为 `Desired=suspended`、`SuspendedFor=token_budget`，再由对账停工作负载；存储保留。用量本身只按 `-activity-flush` 间隔落盘。
- **复用挂起状态**：预算挂起和租约挂起共用 `Desired=suspended`，用 `SuspendedFor` 区分。`blocked()` 对预算挂起返回 `ErrBudgetExceeded`（HTTP 402），租约过期仍是 `ErrExpired`（410）。402 与 410 分开，是因为恢复手段不同：提高预算，而不是续租。
- **续租不解除预算挂起**；提高预算到用量之上（或设为 0）解除，工作区回到 `stopped`，下一次请求唤醒。如果租约同时已过期，它转为租约挂起，宽限期重新计时。
- **预算挂起不会被宽限期硬删**：删除存储必须是显式的 `DELETE`。这是有意的取舍：因为花钱超限而丢掉用户的会话数据，比多留一个挂起的卷更糟。代价是这类卷不会被自动回收。
- **越线有超调**：执行靠心跳，当前这一轮对话会完成。预算限制成本的量级，不是硬上限。
- **上报可信度**：工作负载谎报用量即可绕过预算。预算不是安全边界。

测试：`internal/control/usage_test.go`（契约校验、单调性与回退、立即落盘、挂起/唤醒/恢复、重启后保持、不被宽限期删除、402 的网关行为、指标）、`internal/httpapi/usage_test.go`（端点校验、幂等重放、作用域令牌 404）。
